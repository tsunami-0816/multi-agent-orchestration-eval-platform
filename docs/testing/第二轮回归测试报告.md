## 三、引入新 Bug（修改影响范围内）

> 以下问题是在验证 Bug 修复后的关联功能时，于修改影响的任务执行链路和评测执行链路中新发现的问题。

### REG2-001【P0 致命】orchestration.py 调用不存在的 get_task_by_id 方法，任务状态更新完全失败

| 项目 | 内容 |
|---|---|
| **Bug编号** | REG2-001 |
| **严重等级** | P0 致命 |
| **发现位置** | `app/workers/tasks/orchestration.py:87`（回调载荷加载）、`:132`（状态更新） |
| **Bug描述** | `_update_task_status()` 和 `_load_task_for_callback()` 中调用 `repo.get_task_by_id(task_id)`，但 `TaskRepository` 类中实际定义的方法名是 `get_by_id()`（`task_repo.py:56`）。方法名不匹配导致 `AttributeError: 'TaskRepository' object has no attribute 'get_task_by_id'`，异常被 `_update_task_status` 的 try/except 捕获后仅记录日志，状态更新静默失败。 |
| **复现步骤** | 1. 启动服务（同步降级模式）<br>2. POST `/api/v1/tasks` 创建任务<br>3. 等待编排执行完成（日志显示 graph_complete status=completed）<br>4. GET `/api/v1/tasks/{task_id}` 查询 → **status 永远为 pending**，started_at=null，completed_at=null，result=null |
| **预期结果** | 任务执行完成后 status 应变为 completed，started_at 和 completed_at 应有值，result 应包含编排输出 |
| **影响范围** | ① 任务状态永远停留在 pending，用户无法感知执行进度和结果；② started_at/completed_at/duration_seconds 永远为 NULL；③ 回调载荷无法加载任务信息（completed_at/duration_seconds 缺失）；④ Redis 缓存无法主动失效；⑤ 任务取消、恢复等依赖状态的功能全部失效。**与原 BUG-001 的用户感知症状相同，但根因不同。** |
| **根因定位** | 重构时 TaskRepository 方法名从 `get_task_by_id` 改为 `get_by_id`，但 orchestration.py 中的两处调用方未同步更新。修改 BUG-001/NEW-002 等代码时未发现此不匹配。 |
| **修复建议** | 将 `orchestration.py:87` 和 `:132` 的 `repo.get_task_by_id(task_id)` 改为 `repo.get_by_id(task_id)`。 |

### REG2-002【P1 严重】评测用例同步降级模式下 asyncio.run() 与事件循环冲突，全部用例执行失败

| 项目 | 内容 |
|---|---|
| **Bug编号** | REG2-002 |
| **严重等级** | P1 严重 |
| **发现位置** | `app/eval/eval_service.py:104`（同步降级提交）→ `app/workers/tasks/eval_case.py:43`（asyncio.run） |
| **Bug描述** | 同步降级模式下，`EvalService.create_run()`（async 函数）通过 `asyncio.ensure_future(self._execute_case(...))` 提交用例执行。`_execute_case()` 调用同步函数 `run_eval_case_task()` → `_run_eval_case_sync()` → 内部使用 `asyncio.run(_execute_eval_case(...))`。由于调用链已运行在 FastAPI 的事件循环线程中，`asyncio.run()` 抛出 `RuntimeError: asyncio.run() cannot be called from a running event loop`，所有用例执行失败。 |
| **复现步骤** | 1. 启动服务（同步降级模式，Celery 未启用）<br>2. POST `/api/v1/eval/runs` 创建评测运行（30 个用例）<br>3. 观察服务日志：30 条 `eval_case_task_failed`，错误均为 `asyncio.run() cannot be called from a running event loop`<br>4. GET `/api/v1/eval/runs/{run_id}` → **status 永远为 running，completed_cases=0/30** |
| **预期结果** | 用例应正常执行（Agent编排→Judge评分→写入score→递增进度），全部完成后运行状态变为 completed 并生成报告 |
| **影响范围** | ① 评测用例 100% 执行失败，无评分记录；② completed_cases 永不递增，评测运行永久停留 running；③ 报告永不生成；④ 整个评测执行链路在开发环境（同步降级模式）完全不可用。 |
| **根因定位** | `eval_service.py:104` 的同步降级实现使用 `asyncio.ensure_future` 在当前事件循环中调度，但下游 `_run_eval_case_sync` 设计为独立线程运行（内部用 asyncio.run 创建新事件循环）。两者在同一事件循环线程中冲突。Celery 异步模式下不存在此问题（Worker 进程无预存事件循环）。 |
| **修复建议** | 方案A：`eval_service.py:104` 改用 `asyncio.get_event_loop().run_in_executor(None, lambda: run_eval_case_task(run_id, case_id))`，在独立线程中运行同步函数；方案B：将 `_run_eval_case_sync` 改为纯异步实现，直接 await `_execute_eval_case`，去掉 asyncio.run 包装。 |

### REG2-003【P1 严重】GET /tasks/{task_id}/messages 接口访问不存在的 node 属性，返回 500

| 项目 | 内容 |
|---|---|
| **Bug编号** | REG2-003 |

### 7.2 是否需要再次修复

**本轮回归不通过，必须再次修复。** 理由：

1. **引入 P0 级回归（REG2-001）**：任务状态更新完全失败，用户创建任务后永远看到 pending，无法获取执行结果和耗时。这与原 BUG-001 的用户感知症状相同，核心价值（多Agent编排的可观测性）仍然不可用。

2. **引入 P1 级回归（REG2-002）**：评测用例在开发环境（同步降级模式）下 100% 执行失败，评测运行永远停留 running，报告永不生成。评测是项目三大核心价值之一，执行链路完全不可用。

3. **引入 P1 级回归（REG2-003）**：消息列表接口直接 500，属于接口级功能完全不可用。

4. **三个新 Bug 均位于修改影响的关联链路内**，非范围外问题，必须在本轮闭环。
