# 《第一轮架构评审报告》

**评审对象**：《第一轮技术架构设计文档》v1.0
**基线依据**：《项目基线说明书》v1.0（2026-10-05）
**评审日期**：2026-10-05
**评审范围**：技术选型、分层架构、核心业务链路、数据模型、接口规范、部署架构、监控运维

---

## 评审概述

整体架构分层清晰，技术选型基本符合基线硬约束（LangGraph / MCP / SQLite / FastAPI），核心链路覆盖了编排、工具调用、评测三大场景，数据模型与接口设计较为完整。文档对 11 项技术风险有识别和应对。

但存在 **1 项 P0 级设计缺失**，涉及核心评测链路的并发模型未定义，若按常规方式实现将导致性能指标不达标甚至任务死锁。另有 10 项 P1、10 项 P2 问题需修正或优化。

---

## P0 致命问题（1 项）

### P0-1：评测执行链路的并发模型与 Celery 任务模型未定义，存在死锁与性能不达标风险

**问题描述**：
基线 E-04 要求 30 条用例全量评测 ≤ 5 分钟，文档 §3.3 提出"评测用例并发执行（EVAL_MAX_CONCURRENT=4）"，但全文未明确以下关键决策：

1. **评测引擎如何调用 Agent 编排**：是在评测 Celery 任务进程内直接调用 `OrchestrationService` 执行 LangGraph，还是通过 `POST /api/v1/tasks` 或 `celery delay` 再次投递 Agent 任务？
2. **并发如何实现**：若在单个 Celery 任务内并发执行 4 个 Agent 实例，用线程池还是 asyncio？SQLAlchemy Session、MCP ClientSession、SQLite 写锁在多线程下如何管理？
3. **评测任务本身是否占用 Worker**：评测协调逻辑与 Agent 执行逻辑是否竞争同一个 Worker 池？

若采用最直观的实现——评测任务内为每个用例 `delay` 一个 Agent Celery 任务并 `get()` 等待结果——则构成 **Celery 任务嵌套等待反模式**：默认 `concurrency=2` 时，评测任务占用 1 个 Worker，仅剩 1 个 Worker 可执行 Agent 任务，30 个用例近乎串行（每用例 30-90s），总耗时 15-45 分钟，**E-04 肯定不达标**；若并发调高至评测任务 + 4 个 Agent 任务同时占用 Worker 池，当池满时评测任务等待子任务、子任务等待空闲 Worker，**形成死锁，核心链路完全不通**。

**影响范围**：C-03 评测框架（核心范围）、E-04 评测时间指标、E-03 自动化率、Q-02 性能达标、整体系统可用性。

**严重等级**：P0（符合定义第 2 条"核心性能指标肯定不达标"及第 1 条"核心业务链路可能完全不通"）。

**修改建议**：
明确采用以下方案之一，并在架构文档中补充时序图与并发模型说明：

- **推荐方案——用例级任务拆分（无嵌套）**：评测运行仅作为协调者，`POST /api/v1/eval/runs` 后立即为每条用例独立投递一个 Agent Celery 任务（关联 `run_id`），评测任务本身**不占用 Worker 等待**。`eval_runs.completed_cases` 由各用例任务完成后原子递增，通过轮询 `eval_runs` 状态查看进度。Worker 池全部用于执行 Agent 任务，`concurrency=4` 即满足 4 并发，无嵌套、无死锁。
- **备选方案——任务内线程池直调**：评测任务内用 `ThreadPoolExecutor(max_workers=4)` 直接调用 `LangGraphRunner`（不经过 Celery），每个线程独立创建 SQLAlchemy Session 和 MCP ClientSession，任务结束统一销毁。需补充线程安全说明。

无论选哪种，必须在文档中写明：① 调用路径（函数级 / Celery / HTTP）；② 并发单元与并发数；③ Worker 池大小配置；④ SQLite 写并发控制措施。

## P1 严重问题（10 项）

### P1-1：LangGraph 状态图与多子任务遍历时序矛盾，状态流转设计不完整

**问题描述**：§3.1.1 状态图仅画出单子任务流程 `Planner → Executor → Reviewer → (重试|Aggregator)`，但 Planner 输出的是**子任务列表**，§3.1.2 时序图明确有 `loop 每个子任务`。状态图中缺少"当前子任务执行完毕后，回到 Executor 执行下一个子任务"的条件边，Reviewer 通过后直接指向 Aggregator——按此图实现将只执行第一个子任务就汇总。

**影响范围**：C-01 编排引擎、M-03 完成率、M-02 协作轮次。

**修改建议**：补全状态图，在状态中增加 `current_subtask_idx` 字段；Reviewer 通过后条件路由：`idx < len(subtasks)-1 → Executor（下一个子任务）`，`idx == len(subtasks)-1 → Aggregator`。同时明确 Executor 节点内部工具调用循环（max_tool_calls=5）是节点内循环还是图上边循环。

### P1-2：MCP stdio Session 在 Celery 多进程下的生命周期管理未定义

**问题描述**：§1.2.4 采用 MCP Server 独立进程 + stdio 传输，Agent 侧用 `ClientSession` 通信。但 Agent 任务运行在 Celery prefork Worker 中，文档未说明：① Session 是任务级创建还是全局单例；② 任务异常退出（LLM 超时、Worker 被 kill）时 MCP Server 子进程是否会成为孤儿；③ Worker 进程复用时 Session 是否正确关闭。全局单例会导致多任务串话，任务级创建若缺 `try/finally` 会泄漏子进程与文件描述符。

**影响范围**：C-02 MCP 工具层、T-02 调用成功率、系统稳定性。

**修改建议**：明确 Session 为**任务级**，在任务入口创建、`finally` 块中 `await session.close()` 并确保子进程终止；增加进程泄漏监控（子进程数告警）；禁止 Agent 代码中 `print` 到 stdout（stdio 被 MCP 占用），统一用 logging。

### P1-3：Windows 开发环境与 Celery 5.x 兼容性未明确

**问题描述**：基线 §4.2 要求开发机兼容 Windows 10/11，但 Celery 5.x 官方不再支持 Windows（prefork 不可用，仅 solo/eventlet/gevent 有社区 hack）。§6.6 dev 环境描述为"uvicorn --reload、Mock LLM 模式"，未说明 Celery Worker 在 Windows 本机如何运行；§8.2 R-06 仅提到"用 Docker Desktop 验证 Linux 容器行为"，但未将 dev 环境强制锁定为 Docker。

**影响范围**：开发体验、S-04 一键启动、6 周开发周期。

**修改建议**：在 §6.6 明确：**所有环境（含 dev）必须通过 docker-compose 运行**，不支持 Windows 本机直接运行 Celery；或提供 Windows 下 `celery -A app.worker worker --pool=solo` 的降级方案并说明其并发限制。

### P1-4：任务取消（cancel）机制未设计

**问题描述**：§5.4.1 定义了 `POST /api/v1/tasks/{task_id}/cancel`，但全文未说明取消语义。Celery `revoke` 仅对 PENDING 任务有效，RUNNING 中的任务需 `terminate`（杀进程），而 LangGraph 执行中的任务无法优雅中断——正在进行的 LLM 调用、MCP 工具调用、DB 写入可能处于中间状态。

**影响范围**：C-04 API 层、接口可用性、数据一致性。

**修改建议**：明确取消语义：① PENDING 任务 → Celery revoke，状态置 CANCELLED；② RUNNING 任务 → 置 `cancellation_requested=True`，LangGraph 各节点入口检查该标志后优雅退出，超时未退出则 force terminate；③ 已完成任务 → 返回 409 状态不允许。补充取消后的中间数据清理策略。

### P1-5：结果回调（Webhook）缺失，与基线 C-04 不符

**问题描述**：基线 C-04 明确要求"支持异步提交、状态轮询、结果回调"，但 §5.4 接口清单中仅有状态轮询（`GET /tasks/{id}`），无任何 Webhook 回调注册或推送接口。

**影响范围**：C-04 API 层（核心范围）、基线符合性。

**修改建议**：增加 `POST /api/v1/tasks/{task_id}/webhook`（注册回调 URL）或在提交任务时接受 `callback_url` 参数；任务完成/失败时由 Worker 发起 HTTP POST 回调（含重试）。若时间紧张，可在文档中声明 Webhook 为 P1 优先级延后实现，但必须明确标注，不能静默缺失。

### P1-6：任务状态 Redis 缓存无主动失效机制，可能返回过时状态

**问题描述**：§3.4 任务状态查询采用 Redis 缓存 30s（`SETEX task:{id} 30s`），但 Worker 更新任务状态（PENDING→RUNNING→COMPLETED）后**未说明是否删除对应缓存键**。任务完成后用户在 30s 内查询可能仍看到 RUNNING，极端情况下任务失败也可能被缓存为成功。

**影响范围**：C-05 可观测性、数据一致性、用户体验。

**修改建议**：Worker 每次更新 tasks 表状态后，执行 `DEL task:{task_id}` 使缓存失效；或降低缓存 TTL 至 3-5s 并仅缓存稳定状态（COMPLETED/FAILED），RUNNING 状态不缓存。

### P1-7：web_search 工具实现方案缺失，与基线"不依赖付费 SaaS"约束冲突

**问题描述**：§1.2.4 首批 4 个工具包含 `web_search`，但全文未说明其实现方式。基线 §4.3 明确"不依赖付费 SaaS（除 LLM API 外）"。常规 web_search 需调用 SerpAPI / Tavily / Bing Search 等付费或需注册的服务，与约束冲突。

**影响范围**：C-02 MCP 工具层、T-01 工具数量、基线合规性。

**修改建议**：明确实现方案：① 采用免费且无需 API Key 的方式（如 DuckDuckGo HTML 抓取 + BeautifulSoup 解析）；② 或用 LLM 自身知识模拟搜索（Mock 模式），真实搜索标记为可选；③ 若确实需要第三方 API，需在基线变更记录中说明并获得确认。文档中补充该工具的依赖与调用限制。

### P1-8：code_exec 工具的安全隔离未设计

**问题描述**：`code_exec` 工具允许执行任意代码，但文档未说明任何安全隔离措施。在 Docker 容器内直接 `exec` 用户代码可访问容器文件系统、环境变量（含 API Key）、网络，存在安全风险。即使是单机项目，API 若暴露则风险放大。

**影响范围**：C-02 MCP 工具层、系统安全、API Key 泄露风险。

**修改建议**：至少实现：① 代码在临时目录中执行，禁止挂载敏感路径；② 设置执行超时（如 10s）和内存限制；③ 禁用网络访问（或通过代理白名单）；④ 过滤危险操作（文件删除、环境变量读取）。更完善的方案是用独立 Docker 容器执行代码（Docker-in-Docker 或 sidecar），若时间不足可在文档中声明当前为"可信本地环境"模式并标注风险。

### P1-9：LLM 费用预算控制的计算与持久化未明确

**问题描述**：基线 §4.3 要求 API 预算 ≤¥200，§7.2 告警规则提到"累计 LLM 费用 > ¥180 自动切换 Mock"，但未说明：① Token 消耗量如何换算为费用（不同模型定价不同，DeepSeek 输入/输出分开计价）；② 累计费用存储在哪里（Redis？SQLite？进程内存？），容器重启后是否丢失；③ 切换 Mock 后正在进行的任务如何处理。

**影响范围**：资源约束合规、E-04 评测成本、预算超支风险。

**修改建议**：在 `LLMGateway` 中实现费用计算：按模型配置单价（元/1K tokens），每次调用后累加 `input_tokens * 单价_in + output_tokens * 单价_out`，累计值持久化到 SQLite 表（如 `llm_usage`）或 Redis（开启 AOF）。超过 ¥180 时新任务强制 Mock，在途任务继续完成但告警。

### P1-10：LangGraph 检查点"恢复"与"回放"混淆，恢复接口未设计

**问题描述**：基线 M-04 / C-05 要求"100% 执行步骤可通过 LangGraph state 回放""任意已完成任务可回放完整执行路径"。§4.5 和 §6.4 提到 SqliteSaver 检查点支持"任意节点重入回放"和"Worker 崩溃后可从检查点恢复（需手动触发）"，但**回放**（只读查看历史状态）与**恢复**（从检查点重新执行）是两个不同能力，文档未设计恢复的触发接口（API/CLI），也未说明恢复后任务状态如何流转。

**影响范围**：C-05 可观测性、M-04 可追溯率、故障恢复能力。

**修改建议**：区分两个概念：① 回放——通过 `GET /tasks/{id}/trace` 返回 agent_messages + tool_calls + 检查点快照，只读，当前设计已覆盖；② 恢复——增加 `POST /tasks/{id}/resume` 接口，从指定检查点 `thread_id + checkpoint_id` 重新 `StateGraph.invoke(..., config={"configurable": {"thread_id": ...}, "checkpoint_id": ...})`，恢复后任务状态置 RUNNING 继续执行。若恢复非本期目标，需在文档中明确声明仅支持回放、不支持断点续跑。

## P2 优化建议（10 项）

### P2-1：Celery Beat 非核心功能，增加运维与开发复杂度

**问题描述**：§6.2 引入 `celery-beat` 用于"定时清理过期任务、统计归档"，但这两项均非基线核心范围。1 人 6 周项目中，Beat 的调度逻辑、定时任务幂等性、时区处理会占用开发时间。

**修改建议**：移除 Beat，清理任务改为 CLI 命令手动执行或 API 触发；统计归档直接查 DB 即可。待核心功能稳定后再引入。

### P2-2：Docker 健康检查依赖 curl，但 python:3.12-slim 默认无 curl

**问题描述**：§6.3 健康检查命令为 `curl -f http://localhost:8000/api/v1/health`，但 `python:3.12-slim` 基础镜像不包含 curl，构建时需额外 `apt-get install curl`，增加镜像体积和构建时间。

**修改建议**：改用 `python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/api/v1/health')"` 或安装 `wget`/`curl` 并在 Dockerfile 中明确。

### P2-3：`GET /tasks/{id}/trace` 返回全量数据无分页

**问题描述**：§5.4.1 trace 接口返回 `agent_messages + tool_calls` 全量，长任务（多轮重试 + 多工具调用）可能产生数百条记录，单次响应过大。

**修改建议**：增加 `page` / `page_size` 参数，或按 `round_number` 分段返回。

### P2-4：Prometheus 指标体系（23 个）对单机求职项目过度设计

**问题描述**：§7.1 定义了 14 个业务指标 + 9 个系统指标，且需引入 `prometheus-client` 库。对于单机部署、无 Prometheus Server 采集的场景，大部分指标无人消费。

**修改建议**：精简至 5-8 个核心指标（任务数、完成率、耗时分布、LLM 调用数、工具调用成功率），其余通过日志或 DB 查询获取。

### P2-5：三环境配置（dev/test/prod）对 1 人项目过重

**问题描述**：§6.6 划分 dev/test/prod 三套配置文件 + `APP_ENV` 切换，维护成本高。1 人项目中 test 环境仅 CI 使用，prod 即演示环境。

**修改建议**：简化为单一 `config.yaml` + 环境变量覆盖（Pydantic Settings 原生支持），CI 中通过环境变量注入测试配置。

### P2-6：Alembic 迁移对早期 SQLite 项目可能过重

**问题描述**：引入 Alembic 管理迁移，需维护 migration 脚本、处理 SQLite 的 DDL 限制（如 ALTER TABLE 不支持删列）。项目初期表结构频繁变动，迁移脚本维护成本高。

**修改建议**：开发阶段用 `SQLAlchemy create_all()` 自动建表，待表结构稳定（第 4 周后）再引入 Alembic 并生成初始 migration。文档中明确引入时机。

### P2-7：18 个 API 端点远超基线 ≥5 个要求，部分非核心

**问题描述**：§5.4 共 18 个端点，其中工具手动调用（`/tools/{name}/invoke`）、配置查看（`/config`）、评测用例详情（`/eval/cases/{id}`）等非核心。端点越多，开发和测试工作量越大。

**修改建议**：保留核心 8-10 个（任务提交/状态/结果/取消、评测触发/状态/报告、健康检查），其余标记为 P2 延后或合并。

### P2-8：`init-cases` 命令的幂等性未说明

**问题描述**：§7.3.1 首次启动需执行 `init-cases` 导入用例，但未说明重复执行是否会导致用例重复插入。

**修改建议**：明确 `init-cases` 采用 `INSERT OR IGNORE`（基于 `id` 主键）或 `UPSERT` 语义，重复执行安全。

### P2-9：前端采用轮询获取任务状态，无 SSE/WebSocket 推送

**问题描述**：§2.2.1 前端用"Fetch API 轮询"获取状态，效率低且实时性差。

**修改建议**：本期可保留轮询（满足 P-01 最低要求），文档中标注后续可优化为 SSE（Server-Sent Events），FastAPI 原生支持。

### P2-10：日志双输出（stdout + 文件）在 Docker 环境下冗余

**问题描述**：§7.4 日志同时输出 stdout 和文件（按天轮转保留 7 天）。Docker 环境下 stdout 已被日志驱动收集，文件输出占用容器存储且需额外轮转配置。

**修改建议**：Docker 环境下仅输出 stdout，文件输出仅在非容器化部署时启用（通过配置开关控制）。

## P0 修改后评审结论

**若 P0-1 按建议修改（明确采用"用例级任务拆分、无嵌套等待"方案，并补充并发模型说明），则不存在其他 P0 级问题，架构可以通过评审。**

理由：
- 其余 10 项 P1 均为"可运行但需完善"或"有风险但有缓解路径"，不构成核心链路不通或性能肯定不达标；
- 技术选型（LangGraph + MCP + FastAPI + Celery + Redis + SQLite）无硬冲突，各组件间接口清晰；
- 数据模型、接口规范、部署架构在修正 P1 后可满足基线全部量化指标。

## 最终结论

**修正后通过**

P0-1 必须在开发启动前完成设计修正并更新文档版本；P1 问题建议在详细设计阶段（第 1 周内）逐项明确；P2 问题可在开发过程中按需处理，不阻塞架构评审。
