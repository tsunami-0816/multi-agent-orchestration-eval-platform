    49	### 1.2 关键选型决策说明
    50	
    51	#### 1.2.1 为什么用 Celery + Redis 而非 FastAPI BackgroundTasks
    52	
    53	基线要求任务支持"异步提交、状态轮询、结果回调"，且单任务 P95 ≤ 90s。BackgroundTasks 存在三个硬伤：
    54	
    55	1. **进程耦合**：API 进程重启则所有在途任务丢失，无法满足 M-04（状态可追溯）
    56	2. **无持久化队列**：高并发提交时任务积压在内存，无削峰能力
    57	3. **无重试/超时控制**：Agent 任务涉及外部 LLM API，网络波动时需要自动重试
    58	
    59	Celery + Redis 以 docker-compose 额外一个容器的代价，获得持久化队列、自动重试、超时控制、任务状态持久化等工程能力，且 API 服务与 Worker 解耦后可独立扩缩容。该方案不违反"单机部署"约束（X-01 排除的是 K8s 多节点，非单机多进程）。
    60	
    61	#### 1.2.2 为什么用 SQLAlchemy 而非直接 sqlite3
    62	
    63	- **异步支持**：SQLAlchemy 2.0 的 `asyncio` 引擎与 FastAPI 异步生态一致
    64	- **迁移管理**：Alembic 管理 schema 版本，避免手动 ALTER TABLE
    65	- **类型安全**：Mapped 列定义配合 mypy，减少运行时字段错误
    66	- **可移植性**：若未来需迁移 PostgreSQL，仅改连接串即可
    67	
    68	#### 1.2.3 LLM 后端选型
    69	
    70	| 后端 | 用途 | 接入方式 |
    71	|---|---|---|
    72	| DeepSeek API（默认） | 开发与评测主推理后端 | OpenAI 兼容接口，`langchain-openai` 适配 |
    73	| 通义千问（备选） | 模型对比评测 | OpenAI 兼容接口（DashScope 兼容模式） |
    74	| Ollama + Qwen2.5-7B（可选） | 本地离线推理 | `langchain-ollama` 适配，P-02 配套范围 |
    75	
    76	所有 LLM 调用通过统一的 `LLMGateway` 服务抽象，切换后端仅需修改配置，不改动 Agent 代码。
    77	
    78	#### 1.2.4 MCP 工具实现方式
    79	
    80	采用 **MCP Server 独立进程 + stdio 传输**模式：
    81	
    82	- MCP Server 作为独立 Python 进程运行，通过 stdio/stdout JSON-RPC 与 Agent 通信
    83	- 工具适配器以插件形式注册，新增工具仅需编写一个函数 + JSON Schema 描述（满足 T-03：≤50 行）
    84	- Agent 侧通过 `mcp` Python SDK 的 `ClientSession` 动态发现工具列表并调用
    85	
    86	首批 4 个工具：`web_search`（网页搜索）、`code_exec`（代码执行）、`file_read_write`（文件读写）、`db_query`（数据库查询）。

   226	
   227	### 2.3 层间通信规则
   228	
   229	- **接入层 → 应用层**：同步调用，FastAPI 依赖注入获取 Service 实例
   230	- **应用层 → 服务层**：同步调用（短操作）或 Celery 异步任务（长操作）
   231	- **服务层 → 计算层**：LLM 调用通过 `LLMGateway` 统一出口，禁止 Service 直接调用 SDK
   232	- **服务层 → 存储层**：通过 SQLAlchemy Repository 模式访问，禁止 Service 直接写 SQL
   233	- **跨层调用**：禁止跳层（如 API 直接访问 DB），必须经过 Service 层

   237	## 3. 核心业务链路
   238	
   239	### 3.1 多 Agent 任务执行链路（核心链路）
   240	
   241	#### 3.1.1 状态图定义
   242	
   243	LangGraph StateGraph 包含三个 Agent 节点和一个条件路由：
   244	
   245	```mermaid
   246	stateDiagram-v2
   247	    [*] --> Planner: 输入任务描述
   248	    Planner --> Executor: 拆解为子任务列表
   249	    Executor --> Reviewer: 子任务执行结果
   250	    Reviewer --> Executor: 不通过，需修正<br/>(max_retry=2)
   251	    Reviewer --> Aggregator: 通过
   252	    Aggregator --> [*]: 最终输出
   253	```
   254	
   255	**三个 Agent 角色定义**：
   256	
   257	| 角色 | 职责 | 系统提示词核心 | 可调用工具 |
   258	|---|---|---|---|
   259	| Planner | 任务拆解、子任务排序、依赖分析 | "你是任务规划专家，将复杂任务拆解为可独立执行的子任务" | 无（纯推理） |
   260	| Executor | 执行单个子任务，调用 MCP 工具获取信息 | "你是执行专家，使用可用工具完成子任务" | 全部 MCP 工具 |
   261	| Reviewer | 审查执行结果，判断是否满足子任务目标 | "你是质量审查员，检查结果是否准确、完整、符合要求" | 无（纯推理） |
   262	| Aggregator | 汇总所有子任务结果，生成最终输出 | "你是汇总专家，整合各子任务结果为连贯的最终答案" | 无（纯推理） |
   263	
   264	#### 3.1.2 端到端调用时序
   265	
   266	```mermaid
   267	sequenceDiagram
   268	    participant U as 用户/前端
   269	    participant API as FastAPI
   270	    participant Q as Celery+Redis
   271	    participant W as Celery Worker
   272	    participant LG as LangGraph
   273	    participant P as Planner Agent
   274	    participant E as Executor Agent
   275	    participant R as Reviewer Agent
   276	    participant MCP as MCP Server
   277	    participant LLM as LLM Gateway
   278	    participant DB as SQLite
   279	
   280	    U->>API: POST /api/v1/tasks {input, scenario}
   281	    API->>DB: INSERT task(status=PENDING)
   282	    API->>Q: delay orchestration_task(task_id)
   283	    API-->>U: 202 {task_id, status:PENDING}
   284	
   285	    Q->>W: 分发任务
   286	    W->>DB: UPDATE task(status=RUNNING)
   287	    W->>LG: StateGraph.invoke(input, config={"configurable": {"thread_id": task_id}})
   288	
   289	    LG->>P: Planner 节点
   290	    P->>LLM: chat(messages)
   291	    LLM-->>P: 子任务列表 JSON
   292	    P-->>LG: state.subtasks = [...]
   293	
   294	    loop 每个子任务
   295	        LG->>E: Executor 节点
   296	        E->>MCP: list_tools()
   297	        MCP-->>E: 工具清单
   298	        E->>LLM: chat(messages + tools)
   299	        LLM-->>E: tool_call(name, args)
   300	        E->>MCP: call_tool(name, args)
   301	        MCP-->>E: tool_result
   302	        E->>LLM: chat(messages + tool_result)
   303	        LLM-->>E: 子任务结果
   304	        E-->>LG: state.results[subtask_id] = result
   305	
   306	        LG->>R: Reviewer 节点
   307	        R->>LLM: chat(subtask + result + criteria)
   308	        LLM-->>R: {pass: bool, feedback: str}
   309	        alt 不通过且 retry < 2
   310	            R-->>LG: state.need_revise = True
   311	            LG->>E: 重新执行（携带 feedback）
   312	        else 通过
   313	            R-->>LG: state.reviewed[subtask_id] = True
   314	        end
   315	    end
   316	
   317	    LG->>P: Aggregator 节点（复用 Planner 或独立）
   318	    P->>LLM: chat(all_subtask_results)
   319	    LLM-->>P: 最终输出
   320	    LG-->>W: 最终状态
   321	
   322	    W->>DB: UPDATE task(status=COMPLETED, result=...)
   323	    W->>DB: 写入 agent_messages / tool_calls 记录
   324	```
   325	
   326	#### 3.1.3 各节点输入/处理/输出明细
   327	
   328	| 节点 | 输入 | 处理逻辑 | 输出 |
   329	|---|---|---|---|
   330	| **API 提交** | `{input: str, scenario: str, max_rounds: int?}` | 校验输入 → 创建 DB 记录 → 投递 Celery 任务 | `{task_id: str, status: "PENDING"}` |
   331	| **Planner** | `state.input`（原始任务描述） | LLM 推理 → 解析 JSON 子任务列表 → 写入 `state.subtasks` | `state.subtasks: List[{id, title, description, depends_on}]` |
   332	| **Executor** | `state.subtasks[current]`、`state.tools` | 循环：LLM 决策调工具 → MCP 调用 → 结果回填 → 直到 LLM 输出最终答案或达到 max_tool_calls(=5) | `state.results[subtask_id]: str` |
   333	| **Reviewer** | `state.subtasks[current]`、`state.results[subtask_id]` | LLM 按评分标准判断 pass/fail → 不通过则生成修正反馈 | `state.review[subtask_id]: {pass: bool, feedback: str}` |
   334	| **Aggregator** | `state.results`（全部子任务结果） | LLM 整合为连贯最终输出 | `state.final_output: str` |
   335	| **结果持久化** | `state.final_output`、全量中间状态 | 写入 task 表 + agent_messages 表 + tool_calls 表 | 任务状态更新为 COMPLETED |
   336	
   337	### 3.2 MCP 工具调用链路
   338	
   339	```mermaid
   340	sequenceDiagram
   341	    participant E as Executor Agent
   342	    participant MC as MCP Client
   343	    participant MS as MCP Server
   344	    participant TA as 工具适配器
   345	
   346	    Note over E,TA: 初始化阶段
   347	    E->>MC: 创建 ClientSession(stdio)
   348	    MC->>MS: 启动子进程，stdio 握手
   349	    MS-->>MC: {protocol_version, server_info}
   350	    MC->>MS: tools/list
   351	    MS-->>MC: [{name, description, inputSchema}]
   352	    MC-->>E: 工具清单（注入 LLM function calling）
   353	
   354	    Note over E,TA: 调用阶段
   355	    E->>MC: call_tool(name="web_search", args={query:"..."})
   356	    MC->>MS: JSON-RPC tools/call {name, arguments}
   357	    MS->>TA: 路由到对应适配器
   358	    TA->>TA: JSON Schema 参数校验
   359	    TA->>TA: 执行工具逻辑
   360	    TA-->>MS: {content: [{type:"text", text:"..."}]}
   361	    MS-->>MC: JSON-RPC 响应
   362	    MC-->>E: ToolMessage(content="...")
   363	```

   365	**工具适配器接口规范**：
   366	
   367	```python
   368	class ToolAdapter(Protocol):
   369	    name: str
   370	    description: str
   371	    input_schema: dict  # JSON Schema
   372	
   373	    async def execute(self, **kwargs) -> str:
   374	        """执行工具，返回文本结果"""
   375	        ...
   376	```
   377	
   378	新增工具只需实现该 Protocol 并在 `tools/registry.py` 注册，无需修改 Agent 核心代码（满足 T-03）。

   380	### 3.3 评测执行链路
   381	
   382	```mermaid
   383	flowchart TD
   384	    A[POST /api/v1/eval/runs] --> B[创建 eval_run 记录]
   385	    B --> C[加载用例库 eval_cases]
   386	    C --> D{用例数 > 0?}
   387	    D -->|否| Z[报错: 用例库为空]
   388	    D -->|是| E[投递 Celery 评测任务]
   389	    E --> F[逐用例执行]
   390	    F --> G[调用 Agent 编排获取输出]
   391	    G --> H[LLM-as-Judge 4维度评分]
   392	    H --> I[写入 eval_scores]
   393	    I --> J{还有用例?}
   394	    J -->|是| F
   395	    J -->|否| K[汇总统计: 均值/百分位/通过率]
   396	    K --> L[生成 HTML + JSON 报告]
   397	    L --> M[更新 eval_run status=COMPLETED]
   398	    M --> N[报告可下载]
   399	```
   400	
   401	**评测四维度定义**（E-01）：
   402	
   403	| 维度 | 评分范围 | Judge 提示词要点 |
   404	|---|---|---|
   405	| 准确性（accuracy） | 0-10 | 事实是否正确，有无幻觉 |
   406	| 相关性（relevance） | 0-10 | 是否回应了问题核心，有无答非所问 |
   407	| 完整性（completeness） | 0-10 | 是否覆盖了问题的所有方面 |
   408	| 格式合规性（format） | 0-10 | 是否符合要求的输出格式/结构 |

   713	## 5. 接口规范定义
   714	
   715	### 5.1 统一请求/返回格式
   716	
   717	#### 5.1.1 成功响应
   718	
   719	所有接口返回统一信封格式：
   720	
   721	```json
   722	{
   723	  "code": 0,
   724	  "message": "success",
   725	  "data": { ... },
   726	  "request_id": "req_abc123",
   727	  "timestamp": "2026-10-05T12:00:00Z"
   728	}
   729	```
   730	
   731	| 字段 | 类型 | 说明 |
   732	|---|---|---|
   733	| `code` | int | 业务状态码，0 表示成功，非 0 表示错误 |
   734	| `message` | string | 状态描述 |
   735	| `data` | object/array/null | 业务数据 |
   736	| `request_id` | string | 请求唯一标识，用于日志追踪 |
   737	| `timestamp` | string | 响应时间（ISO 8601 UTC） |
   738	
   739	#### 5.1.2 分页响应
   740	
   741	列表接口的 `data` 字段包含分页信息：
   742	
   743	```json
   744	{
   745	  "code": 0,
   746	  "message": "success",
   747	  "data": {
   748	    "items": [ ... ],
   749	    "total": 100,
   750	    "page": 1,
   751	    "page_size": 20,
   752	    "total_pages": 5
   753	  },
   754	  "request_id": "req_abc123",
   755	  "timestamp": "2026-10-05T12:00:00Z"
   756	}
   757	```
   758	
   759	分页参数：`page`（默认 1）、`page_size`（默认 20，最大 100）。
   760	
   761	#### 5.1.3 错误响应
   762	
   763	```json
   764	{
   765	  "code": 40001,
   766	  "message": "任务输入不能为空",
   767	  "data": null,
   768	  "request_id": "req_abc123",
   769	  "timestamp": "2026-10-05T12:00:00Z",
   770	  "details": {
   771	    "field": "input",
   772	    "reason": "input is required"
   773	  }
   774	}
   775	```
   776	
   777	### 5.2 错误码规范
   778	
   779	采用 5 位数字错误码，前 2 位为模块，后 3 位为具体错误：
   780	
   781	| 错误码范围 | 模块 | HTTP 状态码 |
   782	|---|---|---|
   783	| 0 | 成功 | 200 |
   784	| 10000-10999 | 通用/系统错误 | 500 |
   785	| 20000-20999 | 任务模块错误 | 400/404/409 |
   786	| 30000-30999 | 评测模块错误 | 400/404 |
   787	| 40000-40999 | 工具/MCP 模块错误 | 400/502 |
   788	| 50000-50999 | LLM 网关错误 | 502/504 |
   789	
   790	**常用错误码**：
   791	
   792	| 错误码 | message | HTTP | 说明 |
   793	|---|---|---|---|
   794	| 10001 | 内部服务器错误 | 500 | 未捕获异常 |
   795	| 10002 | 请求参数校验失败 | 400 | Pydantic 校验失败 |
   796	| 10003 | 资源不存在 | 404 | 通用 404 |
   797	| 10004 | 请求过于频繁 | 429 | 限流 |
   798	| 20001 | 任务输入不能为空 | 400 | input 字段为空 |
   799	| 20002 | 任务不存在 | 404 | task_id 无效 |
   800	| 20003 | 任务状态不允许该操作 | 409 | 如对已完成任务取消 |
   801	| 20004 | 任务执行失败 | 500 | Worker 执行异常 |
   802	| 30001 | 评测用例库为空 | 400 | 无可用用例 |
   803	| 30002 | 评测运行不存在 | 404 | run_id 无效 |
   804	| 30003 | 报告尚未生成 | 404 | 评测未完成 |
   805	| 40001 | MCP 工具不存在 | 400 | 工具名未注册 |
   806	| 40002 | 工具参数校验失败 | 400 | JSON Schema 校验不通过 |
   807	| 40003 | 工具执行超时 | 504 | 工具调用超时 |
   808	| 50001 | LLM API 调用失败 | 502 | 外部 API 错误 |
   809	| 50002 | LLM API 超时 | 504 | 超过超时阈值 |
   810	| 50003 | LLM API 配额不足 | 429 | 触发预算保护 |

   812	### 5.3 鉴权规则
   813	
   814	鉴于基线明确排除多租户/用户权限体系（X-02），采用**轻量级 API Key 机制**：
   815	
   816	- 环境变量 `API_KEY` 配置一个全局密钥（可选，未设置则不鉴权）
   817	- 客户端通过请求头 `X-API-Key: <key>` 传递
   818	- 仅对写操作（POST/PUT/DELETE）强制鉴权，读操作（GET）开放
   819	- 密钥不存入数据库，仅在内存中比对
   820	- 预留 `AuthMiddleware` 扩展点，未来可替换为 JWT/OAuth

   878	
   879	```mermaid

   902	### 6.2 docker-compose 服务定义
   903	
   904	| 服务名 | 镜像 | 端口 | 依赖 | 说明 |
   905	|---|---|---|---|---|
   906	| `api` | 本地构建（python:3.12-slim） | 8000:8000 | redis | FastAPI 服务，托管前端静态文件 |
   907	| `worker` | 同 api 镜像（command: celery -A app.worker worker） | — | redis | Celery Worker，执行 Agent 编排任务 |
   908	| `beat` | 同 api 镜像（command: celery -A app.worker beat） | — | redis | 定时任务（清理过期任务、统计归档） |
   909	| `redis` | redis:7.4-alpine | 6379（仅内部） | — | Celery broker + 缓存 |
   910	| `ollama`（可选） | ollama/ollama:latest | 11434（仅内部） | — | 本地模型，通过 profile 选择性启动 |

   916	### 6.3 容器构建策略
   917	
   918	采用**多阶段构建**减小镜像体积：
   919	
   920	```
   921	Stage 1 (builder): python:3.12-slim → 安装依赖 → 编译
   922	Stage 2 (runtime): python:3.12-slim → 拷贝 site-packages + 代码 → 非 root 用户运行
   923	```
   924	
   925	- 最终镜像目标 < 500MB
   926	- 不安装开发依赖（pytest、ruff、mypy）
   927	- 健康检查：`curl -f http://localhost:8000/api/v1/health`
   928	
   929	### 6.4 高可用方案
   930	
   931	基线 X-06 明确"生产级高可用/灾备"不在范围内，但设计上保留以下基础保障：
   932	
   933	| 维度 | 方案 | 说明 |
   934	|---|---|---|
   935	| API 无状态 | FastAPI 实例无状态，可启动多个副本（`docker-compose up --scale api=3`） | 需前置负载均衡（如 nginx），默认单副本 |
   936	| Worker 水平扩展 | Celery Worker 可多副本，`--concurrency` 控制单进程并发 | 默认 concurrency=2，可根据 CPU 调整 |
   937	| 任务持久化 | Redis 持久化（AOF）+ SQLite 任务状态 | 容器重启不丢失任务 |
   938	| 检查点恢复 | LangGraph SqliteSaver 持久化状态 | Worker 崩溃后可从检查点恢复（需手动触发） |
   939	| 健康检查 | docker-compose healthcheck 自动重启异常容器 | `restart: unless-stopped` |

  1111	## 8. 技术风险与应对方案
  1112	
  1113	### 8.1 核心风险
  1114	
  1115	#### 风险 R-01：LangGraph 状态管理复杂度
  1116	
  1117	| 项 | 内容 |
  1118	|---|---|
  1119	| **风险描述** | 多 Agent 协作涉及 Planner→Executor→Reviewer 循环 + 条件路由，StateGraph 状态字段多、流转复杂，易出现状态不一致或死循环 |
  1120	| **影响范围** | C-01 编排引擎，M-03 完成率、M-04 可追溯率 |
  1121	| **概率** | 高 |
  1122	| **严重度** | 高 |
  1123	| **应对方案** | ① 状态字段用 Pydantic 模型严格定义，每个节点只写入自己负责的字段；② 设置 `max_rounds=5` 硬上限防止死循环（满足 M-02）；③ Reviewer 不通过时最多重试 2 次后强制通过并记录 warning；④ 每个节点入口/出口打印状态快照，便于调试；⑤ 单元测试覆盖每条状态转移路径 |
  1124	
  1125	#### 风险 R-02：MCP 协议稳定性与工具调用可靠性
  1126	
  1127	| 项 | 内容 |
  1128	|---|---|
  1129	| **风险描述** | MCP 协议尚在快速演进，Python SDK API 可能变更；stdio 传输在 Windows 下可能有编码/缓冲问题；工具执行异常可能导致 Agent 卡死 |
  1130	| **影响范围** | C-02 MCP 工具层，T-02 调用成功率 |
  1131	| **概率** | 中 |
  1132	| **严重度** | 高 |
  1133	| **应对方案** | ① 锁定 MCP SDK 版本（`mcp==0.1.x`），不随意升级；② 工具调用设置 30s 超时，超时返回结构化错误而非挂起；③ 工具适配器统一 try/except，异常转为 ToolMessage error 格式，Agent 可感知并决策；④ JSON Schema 参数校验在调用前执行（T-04），减少非法调用；⑤ Windows 下 stdio 强制 UTF-8 编码（`PYTHONIOENCODING=utf-8`） |
  1134	
  1135	#### 风险 R-03：LLM API 不稳定与预算超限
  1136	
  1137	| 项 | 内容 |
  1138	|---|---|
  1139	| **风险描述** | 外部 LLM API 可能限流、超时、返回格式异常；API 预算 ≤¥200，评测 30 用例 × 多轮调用可能超支 |
  1140	| **影响范围** | 全链路，E-04 评测时间、Q-02 性能 |
  1141	| **概率** | 中 |
  1142	| **严重度** | 高 |
  1143	| **应对方案** | ① LLM Gateway 实现指数退避重试（最多 3 次，初始 1s）；② 响应格式校验，非预期 JSON 时自动重试一次并附加格式提醒；③ **Mock 模式**：评测框架支持 `--mock` 参数，用预设响应替代真实 LLM 调用，开发调试零成本；④ Token 用量实时累计，超过 ¥180 阈值自动告警并切换 Mock；⑤ 评测用例支持分批执行（`--category` 筛选），控制单次消耗 |
  1144	
  1145	#### 风险 R-04：LLM-as-Judge 评分一致性不足
  1146	
  1147	| 项 | 内容 |
  1148	|---|---|
  1149	| **风险描述** | LLM 评分存在随机性，同一输出多次评分可能差异较大，Spearman 相关系数可能低于 0.7（E-05） |
  1150	| **影响范围** | C-03 评测框架，E-05 评分一致性 |
  1151	| **概率** | 中 |
  1152	| **严重度** | 中 |
  1153	| **应对方案** | ① Judge 提示词严格约束输出格式（JSON + 分数 + 理由），降低随机性；② 每个用例评分 2 次取平均，减少单次波动；③ 评分标准（`scoring_criteria`）在用例中明确定义，Judge 严格按标准打分；④ 温度设为 0（`temperature=0`），最大化确定性；⑤ 定期用 10 条标注用例做一致性校验，低于 0.7 时优化提示词 |
  1154	
  1155	### 8.2 兼容性风险
  1156	
  1157	#### 风险 R-05：Python 版本与依赖冲突
  1158	
  1159	| 项 | 内容 |
  1160	|---|---|
  1161	| **风险描述** | LangGraph 0.2 + LangChain 0.3 + Pydantic v2 组合较新，部分子依赖可能要求 Pydantic v1，导致冲突 |
  1162	| **概率** | 中 |
  1163	| **应对方案** | ① 使用 `pip-compile` 锁定全量依赖版本（requirements.lock）；② CI 矩阵在 Python 3.10 和 3.12 上跑安装测试；③ 遇到 Pydantic v1/v2 冲突的库，寻找替代或使用 `pydantic.v1` 兼容模块 |
  1164	
  1165	#### 风险 R-06：Windows 与 Linux 行为差异
  1166	
  1167	| 项 | 内容 |
  1168	|---|---|
  1169	| **风险描述** | 开发在 Windows，部署在 Linux 容器；文件路径分隔符、进程信号处理、sqlite 并发锁行为可能不同 |
  1170	| **概率** | 中 |
  1171	| **应对方案** | ① 所有路径使用 `pathlib.Path`，不硬编码分隔符；② SQLite 开启 WAL 模式（`PRAGMA journal_mode=WAL`）提升并发读写；③ 开发阶段用 Docker Desktop 验证 Linux 容器行为，不依赖本机 Python；④ CI 在 Ubuntu runner 上跑全量测试 |
  1172	
  1173	#### 风险 R-07：SQLite 并发写入瓶颈
  1174	
  1175	| 项 | 内容 |
  1176	|---|---|
  1177	| **风险描述** | SQLite 写锁为库级锁，多 Worker 并发写入任务状态时可能出现 `database is locked` 错误 |
  1178	| **概率** | 中（评测并发时） |
  1179	| **应对方案** | ① WAL 模式允许读写并发；② 设置 `busy_timeout=5000ms`，写冲突时等待而非立即报错；③ 评测场景下 Worker concurrency 控制在 ≤4；④ 高频写入（如 agent_messages）采用批量插入；⑤ 若仍有瓶颈，可将检查点库与业务库分离为两个文件 |
  1180	
  1181	### 8.3 性能风险
  1182	
  1183	#### 风险 R-08：单任务响应延迟超标
  1184	
  1185	| 项 | 内容 |
  1186	|---|---|
  1187	| **风险描述** | 多 Agent 多轮 + 工具调用 + LLM 推理，单任务可能超过 P95 ≤ 90s 目标（M-05/Q-02） |
  1188	| **概率** | 中 |
  1189	| **应对方案** | ① Planner 一次性拆解全部子任务，Executor 按依赖关系并行执行无依赖的子任务（asyncio.gather）；② 工具调用超时 30s，避免单个工具拖慢全局；③ LLM 调用设置合理 timeout（60s）+ 流式响应（如支持）；④ 评测时预热 LLM 连接（连接池复用）；⑤ 若 P95 持续超标，优化提示词减少轮次，或降低 max_rounds 到 3 |
  1190	
  1191	#### 风险 R-09：评测全量执行超时
  1192	
  1193	| 项 | 内容 |
  1194	|---|---|
  1195	| **风险描述** | 30 用例 × 每用例多轮 Agent + Judge 评分，可能超过 5 分钟（E-04） |
  1196	| **概率** | 中 |
  1197	| **应对方案** | ① 评测用例并发执行（`EVAL_MAX_CONCURRENT=4`），而非串行；② Judge 评分与 Agent 执行 pipeline 化（Agent 完成一个立即评分，不等全部完成）；③ Mock 模式下评测应 < 1 分钟；④ 真实 API 模式下若超时，提供 `--batch` 参数分批执行 |
