    81	### 1.2 关键选型决策说明
    82	
    83	#### 1.2.1 为什么用 Celery + Redis 而非 FastAPI BackgroundTasks
    84	
    85	基线要求任务支持"异步提交、状态轮询、结果回调"，且单任务 P95 ≤ 90s。BackgroundTasks 存在三个硬伤：
    86	
    87	1. **进程耦合**：API 进程重启则在途任务丢失，无法满足 M-04（状态可追溯）
    88	2. **无持久化队列**：高并发提交时任务积压在内存，无削峰能力
    89	3. **无重试/超时控制**：Agent 任务涉及外部 LLM API，网络波动时需自动重试
    90	
    91	Celery + Redis 以额外一个容器的代价，获得持久化队列、自动重试、超时控制、任务状态持久化。该方案不违反"单机部署"约束（X-01 排除的是 K8s 多节点，非单机多进程）。
    92	
    93	#### 1.2.2 为什么用 SQLAlchemy 而非直接 sqlite3
    94	
    95	- **异步支持**：SQLAlchemy 2.0 的 asyncio 引擎与 FastAPI 异步生态一致
    96	- **类型安全**：Mapped 列定义配合 mypy，减少运行时字段错误
    97	- **可移植性**：未来迁移 PostgreSQL 仅改连接串
    98	- **迁移管理**：第 4 周表结构稳定后引入 Alembic（P2-6），开发期用 `create_all()`
    99	
   100	#### 1.2.3 LLM 后端选型

   109	所有 LLM 调用通过统一的 `LLMGateway` 服务抽象，切换后端仅需修改配置。**费用计算与预算控制见 §3.8（P1-9 修正）**。
   110	
   111	#### 1.2.4 MCP 工具实现方式（P1-7 / P1-8 修正）
   112	
   113	采用 **MCP Server 独立进程 + stdio 传输**模式：
   114	
   115	- MCP Server 作为独立 Python 进程运行，通过 stdio/stdout JSON-RPC 与 Agent 通信
   116	- 工具适配器以插件形式注册，新增工具仅需编写一个函数 + JSON Schema 描述（满足 T-03：≤50 行）
   117	- Agent 侧通过 `mcp` Python SDK 的 `ClientSession` 动态发现工具列表并调用
   118	
   119	**首批 4 个工具及实现方案**：
   120	
   121	| 工具名 | 功能 | 实现方案 | 安全措施 |
   122	|---|---|---|---|
   123	| `web_search` | 网页搜索 | **DuckDuckGo HTML 抓取 + BeautifulSoup 解析**（P1-7）：requests 请求 DuckDuckGo 搜索结果页，BS4 提取标题/链接/摘要，返回 Top 5。免费、无需 API Key、不依赖付费 SaaS | 请求超时 10s，User-Agent 伪装，结果缓存 5 分钟 |
   124	| `code_exec` | 代码执行 | `subprocess.run` 在临时目录执行 Python 代码（P1-8） | ① 临时目录 `/tmp/code_exec_{uuid}/`，禁止挂载敏感路径；② 执行超时 10s（`timeout` 参数）；③ 内存限制通过 `resource.setrlimit`（Linux）/ 进程超时兜底；④ 危险操作过滤：禁止 `os.remove`、`shutil.rmtree`、环境变量读取、`socket` 网络操作；⑤ 声明为"可信本地环境"模式，API 暴露时需额外加固 |
   125	| `file_read_write` | 文件读写 | 限定工作目录 `data/workspace/` 内的文件读写 | 路径白名单校验，禁止 `..` 穿越，单文件 ≤ 1MB |
   126	| `db_query` | 数据库查询 | 只读 SQL 查询，连接业务 SQLite 库 | 仅允许 SELECT 语句，禁止 INSERT/UPDATE/DELETE/DROP，查询超时 5s，结果行数上限 1000 |
   127	
   128	**工具适配器接口规范**：
   129	
   130	```python
   131	class ToolAdapter(Protocol):
   132	    name: str
   133	    description: str
   134	    input_schema: dict  # JSON Schema
   135	
   136	    async def execute(self, **kwargs) -> str:
   137	        """执行工具，返回文本结果"""
   138	        ...
   139	```
   140	
   141	新增工具只需实现该 Protocol 并在 `tools/registry.py` 注册，无需修改 Agent 核心代码（满足 T-03）。

   292	
   293	- **接入层 → 应用层**：同步调用，FastAPI 依赖注入获取 Service 实例
   294	- **应用层 → 服务层**：同步调用（短操作）或 Celery 异步任务（长操作）
   295	- **服务层 → 计算层**：LLM 调用通过 `LLMGateway` 统一出口，禁止 Service 直接调用 SDK
   296	- **服务层 → 存储层**：通过 SQLAlchemy Repository 模式访问，禁止 Service 直接写 SQL
   297	- **跨层调用**：禁止跳层（如 API 直接访问 DB），必须经过 Service 层
   298	- **回调方向**：应用层 CallbackService → 外部 Webhook（HTTP POST），不经过服务层

   303	
   304	### 3.1 多 Agent 任务执行链路（核心链路）
   305	
   306	#### 3.1.1 状态图定义（P1-1 修正：补全子任务遍历）
   307	
   308	**LangGraph State 定义**：
   309	
   310	```python
   311	class SubTask(TypedDict):
   312	    id: str
   313	    title: str
   314	    description: str
   315	    depends_on: list[str]  # 依赖的子任务 id
   316	
   317	class ReviewResult(TypedDict):
   318	    passed: bool
   319	    feedback: str
   320	
   321	class AgentState(TypedDict):
   322	    input: str                          # 原始任务描述
   323	    subtasks: list[SubTask]             # Planner 拆解的子任务列表
   324	    current_subtask_idx: int            # 当前执行的子任务索引（P1-1 新增）
   325	    results: dict[str, str]             # 子任务 id → 执行结果
   326	    review_results: dict[str, ReviewResult]  # 子任务 id → 审查结果
   327	    revise_count: dict[str, int]        # 子任务 id → 已重试次数
   328	    final_output: str                   # 最终汇总输出
   329	    max_tool_calls: int                 # 单节点最大工具调用次数，默认 5
   330	```
   331	
   332	**状态图（含子任务遍历条件边）**：
   333	
   334	```mermaid
   335	stateDiagram-v2
   336	    [*] --> Planner: 输入任务描述
   337	    Planner --> Executor: 拆解为子任务列表<br/>current_subtask_idx=0
   338	
   339	    state "Executor 节点" as Exec
   340	    state "Reviewer 节点" as Rev
   341	
   342	    Exec --> Rev: 子任务执行结果<br/>(节点内工具调用循环 max_tool_calls=5)
   343	
   344	    Rev --> Exec: 不通过且 revise_count<2<br/>携带 feedback 重试
   345	    Rev --> Exec: 通过且 idx < len(subtasks)-1<br/>idx+=1, 执行下一个子任务
   346	    Rev --> Aggregator: 通过且 idx == len(subtasks)-1<br/>所有子任务完成
   347	    Aggregator --> [*]: 最终输出
   348	```
   349	
   350	**条件边逻辑**（`after_reviewer` 函数）：
   351	
   352	```python
   353	def after_reviewer(state: AgentState) -> str:
   354	    idx = state["current_subtask_idx"]
   355	    current_id = state["subtasks"][idx]["id"]
   356	    review = state["review_results"].get(current_id)
   357	
   358	    # 不通过且未达重试上限 → 回到 Executor 重试
   359	    if review and not review["passed"] and state["revise_count"].get(current_id, 0) < 2:
   360	        state["revise_count"][current_id] = state["revise_count"].get(current_id, 0) + 1
   361	        return "executor"
   362	
   363	    # 通过（或重试耗尽强制通过）→ 判断是否还有下一个子任务
   364	    if idx < len(state["subtasks"]) - 1:
   365	        state["current_subtask_idx"] = idx + 1
   366	        return "executor"  # 执行下一个子任务
   367	    else:
   368	        return "aggregator"  # 所有子任务完成，进入汇总
   369	```
   370	
   371	**关键设计决策**：
   372	- **Executor 节点内工具调用循环**：工具调用（LLM 决策 → MCP 调用 → 结果回填）是 **Executor 节点内部的 while 循环**（`max_tool_calls=5`），不是图上边循环。节点入口时创建 MCP Session，节点出口时关闭（见 §3.2.3）。
   373	- **重试耗尽策略**：Reviewer 不通过最多重试 2 次，第 3 次强制标记为通过并记录 warning，避免死循环。
   374	- **current_subtask_idx**：P1-1 新增字段，确保子任务逐个遍历，不会只执行第一个就汇总。
   375	
   376	**四个 Agent 角色定义**：
   377	
   378	| 角色 | 职责 | 系统提示词核心 | 可调用工具 |
   379	|---|---|---|---|
   380	| Planner | 任务拆解、子任务排序、依赖分析 | "你是任务规划专家，将复杂任务拆解为可独立执行的子任务，输出 JSON 格式" | 无（纯推理） |
   381	| Executor | 执行单个子任务，调用 MCP 工具获取信息 | "你是执行专家，使用可用工具完成子任务，必要时多次调用工具" | 全部 MCP 工具 |
   382	| Reviewer | 审查执行结果，判断是否满足子任务目标 | "你是质量审查员，检查结果是否准确、完整、符合要求，输出 {passed, feedback}" | 无（纯推理） |
   383	| Aggregator | 汇总所有子任务结果，生成最终输出 | "你是汇总专家，整合各子任务结果为连贯的最终答案" | 无（纯推理） |

   386	
   387	```mermaid
   388	sequenceDiagram
   389	    participant U as 用户/前端

   391	    participant Q as Celery+Redis
   392	    participant W as Celery Worker
   393	    participant LG as LangGraph
   394	    participant P as Planner
   395	    participant E as Executor
   396	    participant R as Reviewer
   397	    participant A as Aggregator

   399	    participant LLM as LLM Gateway
   400	    participant DB as SQLite
   401	    participant CB as CallbackService
   402

   404	    API->>DB: INSERT task(status=PENDING, callback_url=...)

   409	    W->>DB: UPDATE task(status=RUNNING, started_at=now)

   414	    LG->>P: Planner 节点
   415	    P->>LLM: chat(messages)

   420	        LG->>E: Executor 节点 (创建 MCP Session)

   437	            LG->>E: 重新执行（携带 feedback）
   438	        else 通过或重试耗尽
   439	            R-->>LG: state.review_results[id]={passed:True}

   442	
   443	    LG->>A: Aggregator 节点

   445	    LLM-->>A: 最终输出
   446	    A-->>LG: state.final_output=...
   447	    LG-->>W: 最终状态

   450	    W->>DB: 批量写入 agent_messages / tool_calls
   451	    W->>REDIS: DEL task:{task_id} (缓存失效)
   452	
   453	    alt 存在 callback_url (P1-5)
   454	        W->>CB: 触发回调
   455	        CB->>U: HTTP POST {task_id, status, result} (含重试, 最多3次)

   459	#### 3.1.3 各节点输入/处理/输出明细
   460	
   461	| 节点 | 输入 | 处理逻辑 | 输出 |
   462	|---|---|---|---|
   463	| **API 提交** | `{input: str, scenario: str?, max_rounds: int?, callback_url: str?}` | 校验输入 → 创建 DB 记录 → 投递 Celery 任务 → 返回 202 | `{task_id: str, status: "PENDING"}` |
   464	| **Planner** | `state.input` | LLM 推理 → 解析 JSON 子任务列表 → 写入 state.subtasks，重置 current_subtask_idx=0 | `state.subtasks: List[SubTask]` |
   465	| **Executor** | `state.subtasks[current]`、`state.tools` | 创建 MCP Session → 循环：LLM 决策调工具 → MCP 调用 → 结果回填 → 直到 LLM 输出最终答案或达到 max_tool_calls(=5) → finally 关闭 Session | `state.results[subtask_id]: str` |
   466	| **Reviewer** | `state.subtasks[current]`、`state.results[subtask_id]` | LLM 按评分标准判断 passed/fail → 不通过生成 feedback → 写入 review_results | `state.review_results[subtask_id]: ReviewResult` |
   467	| **条件路由** | `state.current_subtask_idx`、review_results、revise_count | ① 不通过且 retry<2 → Executor（重试）② 通过且 idx<N-1 → idx+=1, Executor（下一子任务）③ 通过且 idx=N-1 → Aggregator | 路由目标节点名 |
   468	| **Aggregator** | `state.results`（全部子任务结果） | LLM 整合为连贯最终输出 | `state.final_output: str` |
   469	| **结果持久化** | `state.final_output`、全量中间状态 | 写入 task 表 + 批量写入 agent_messages/tool_calls 表 → DEL Redis 缓存 | 任务状态更新为 COMPLETED |
   470	| **回调通知** | `task.callback_url`、任务结果 | httpx 异步 POST 回调 → 失败指数退避重试（最多 3 次） | 回调响应（仅日志记录） |

   525	#### 3.2.3 MCP Session 生命周期管理（P1-2 修正）
   526	
   527	**核心原则：Session 为任务级，非全局单例。**
   528	
   529	| 阶段 | 操作 | 实现细节 |
   530	|---|---|---|
   531	| **创建** | Celery 任务入口、Executor 节点首次调用工具前 | `ClientSession(stdioTransport(read, write))`，通过 `subprocess.Popen` 启动 MCP Server 子进程 |
   532	| **使用** | Executor 节点内工具调用循环 | 同一 Session 复用，list_tools 仅调用一次缓存 |
   533	| **关闭** | Executor 节点出口的 `finally` 块 | `await session.close()` → 发送 shutdown → `process.terminate()` → `wait(timeout=5)` → 未退出则 `process.kill()` |
   534	| **异常清理** | 任务异常退出（LLM 超时、Worker kill） | Celery 任务 `after_return` 钩子 + `try/finally` 双重保障，确保子进程终止 |
   535	| **进程泄漏监控** | 运维层 | 定期检查子进程数，超过阈值（如 >10）告警；Worker 启动时清理孤儿 MCP 进程 |
   536	
   537	**禁止事项**：
   538	- 禁止 Agent 代码中 `print()` 到 stdout（stdio 被 MCP 占用，会干扰 JSON-RPC 通信），统一用 `logging`
   539	- 禁止全局单例 Session（多任务串话）
   540	- 禁止在非 finally 块中关闭 Session（异常时泄漏）
   541	
   542	### 3.3 评测执行链路（P0-1 修正：用例级任务拆分、无嵌套等待）
   543	
   544	#### 3.3.1 并发模型核心设计
   545	
   546	**采用方案：用例级任务拆分（无嵌套等待）**
   547	
   548	| 决策项 | 方案 |
   549	|---|---|
   550	| 调用路径 | API 层直接为每条用例 `delay` 一个 Agent Celery 任务，**评测协调逻辑不占用 Worker** |
   551	| 并发单元 | 每条评测用例 = 一个独立 Celery 任务（内部执行 LangGraph + Judge 评分） |
   552	| 并发数 | Worker `concurrency=4`，即最多 4 个用例同时执行 |
   553	| Worker 池 | 全部用于执行 Agent 任务（普通任务 + 评测用例任务共享同一池），无评测协调任务占用 |
   554	| 进度跟踪 | `eval_runs.completed_cases` 由各用例任务完成后**原子递增**（`UPDATE ... SET completed_cases = completed_cases + 1`） |
   555	| 死锁风险 | **无**：不存在任务嵌套等待，不存在"评测任务等子任务、子任务等空闲 Worker"的循环 |
   556	
   557	**性能估算**（验证 E-04 ≤5 分钟）：
   558	- 30 用例 ÷ 4 并发 = 7.5 批
   559	- 单用例平均耗时：Agent 执行（Planner 1 次 + Executor 2-3 次 LLM + Reviewer 1 次 ≈ 15-25s）+ Judge 评分（1 次 LLM ≈ 3-5s）≈ 20-30s
   560	- 总耗时 ≈ 7.5 × 25s ≈ 187s ≈ **3.1 分钟**，满足 ≤5 分钟
   561	- 最坏情况（每用例 90s P95）：7.5 × 90s = 675s ≈ 11 分钟 → 此时可临时提升 concurrency 至 6（需 CPU 允许），或用 `--batch` 分批
   562	
   563	#### 3.3.2 端到端流程
   564	
   565	```mermaid
   566	flowchart TD
   567	    A[POST /api/v1/eval/runs] --> B[创建 eval_run 记录<br/>status=PENDING, total_cases=N]
   568	    B --> C[加载启用的评测用例列表]
   569	    C --> D{用例数 > 0?}
   570	    D -->|否| Z[返回 400: 用例库为空]
   571	    D -->|是| E[UPDATE eval_run status=RUNNING]
   572	    E --> F[循环每条用例:<br/>delay eval_case_task(run_id, case_id)]
   573	    F --> G[立即返回 202 {run_id, status:RUNNING}]
   574	
   575	    subgraph Celery Worker 池 (concurrency=4)
   576	        H1[用例任务 1]
   577	        H2[用例任务 2]
   578	        H3[用例任务 3]
   579	        H4[用例任务 4]
   580	        H5[用例任务 5...N]
   581	    end
   582	
   583	    H1 --> I1[执行 LangGraph 编排<br/>获取 Agent 输出]
   584	    I1 --> J1[LLM-as-Judge 4维度评分]
   585	    J1 --> K1[写入 eval_scores]
   586	    K1 --> L1[原子递增 eval_runs.completed_cases<br/>UPDATE SET completed_cases=completed_cases+1]
   587	    L1 --> M1{completed_cases == total_cases?}
   588	
   589	    H2 & H3 & H4 & H5 --> I1
   590	
   591	    M1 -->|否| N[任务结束, Worker 释放]
   592	    M1 -->|是| O[最后一个完成的用例任务<br/>触发报告生成]
   593	    O --> P[汇总统计: 均值/百分位/通过率]
   594	    P --> Q[生成 HTML + JSON 报告]
   595	    Q --> R[UPDATE eval_run status=COMPLETED]
   596	    R --> S[报告可下载]
   597	
   598	    U[用户轮询 GET /eval/runs/{run_id}] --> V[读取 eval_run 进度]
   599	```
   600	
   601	#### 3.3.3 用例任务内部流程
   602	
   603	每个 `eval_case_task(run_id, case_id)` Celery 任务执行以下步骤：
   604	
   605	| 步骤 | 操作 | 输入 | 输出 |
   606	|---|---|---|---|
   607	| 1 | 加载用例详情 | case_id | `{input, expected_output, scoring_criteria}` |
   608	| 2 | 创建关联 task 记录 | run_id, case_id, input | task_id（status=PENDING） |
   609	| 3 | 执行 LangGraph 编排 | task_id, input | Agent 输出（同 §3.1） |
   610	| 4 | LLM-as-Judge 评分 | 用例输入、Agent 输出、scoring_criteria | 4 维度分数 + feedback |
   611	| 5 | 写入 eval_scores | run_id, case_id, task_id, 分数 | 评分记录 |
   612	| 6 | 原子递增 completed_cases | run_id | eval_runs 表更新 |
   613	| 7 | 判断是否为最后一个 | completed_cases == total_cases | 若是则触发报告生成 |
   614	| 8 | 任务结束 | — | Worker 释放 |
   615	
   616	**SQLite 写并发控制**（P0-1 要求）：
   617	- 业务库开启 WAL 模式（`PRAGMA journal_mode=WAL`），读写不互斥
   618	- `busy_timeout=5000ms`，写冲突时等待而非立即报错
   619	- `completed_cases` 原子递增使用单条 `UPDATE eval_runs SET completed_cases = completed_cases + 1 WHERE id = ?`，SQLite 单条写操作原子
   620	- 评测场景 Worker concurrency 控制在 ≤4，避免过度竞争
   621	
   622	### 3.4 任务取消链路（P1-4 修正）
   623	
   624	#### 3.4.1 取消语义
   625	
   626	| 任务状态 | 取消操作 | 结果 |
   627	|---|---|---|
   628	| **PENDING**（队列中未执行） | Celery `revoke(task_id)` | 状态置 CANCELLED，Worker 领取时跳过 |
   629	| **RUNNING**（执行中） | ① 置 `cancellation_requested=True`（DB 字段）② LangGraph 各节点入口检查该标志 → 优雅退出 ③ 超时 30s 未退出 → `celery control terminate`（杀 Worker 进程） | 状态置 CANCELLED，中间数据保留 |
   630	| **COMPLETED / FAILED / CANCELLED** | 不允许取消 | 返回 409 状态冲突 |
   631	
   632	#### 3.4.2 取消时序
   633	
   634	```mermaid
   635	sequenceDiagram
   636	    participant U as 用户
   637	    participant API as FastAPI
   638	    participant DB as SQLite
   639	    participant Q as Celery+Redis
   640	    participant W as Celery Worker
   641	    participant LG as LangGraph
   642	
   643	    U->>API: POST /api/v1/tasks/{task_id}/cancel
   644	    API->>DB: SELECT status FROM tasks WHERE id=?
   645	    alt status=PENDING
   646	        API->>Q: revoke(task_id)
   647	        API->>DB: UPDATE task SET status=CANCELLED
   648	        API-->>U: 200 {status:CANCELLED}
   649	    else status=RUNNING
   650	        API->>DB: UPDATE task SET cancellation_requested=True
   651	        API-->>U: 202 {status:RUNNING, message:"取消请求已提交"}
   652	        Note over W,LG: Worker 在下一个节点入口检查标志
   653	        W->>DB: 轮询 cancellation_requested (每节点入口)
   654	        alt 30s 内优雅退出
   655	            W->>DB: UPDATE task SET status=CANCELLED
   656	            W->>DB: 保留中间数据(agent_messages/tool_calls)
   657	        else 超时未退出
   658	            API->>Q: celery control terminate(task_id, signal=SIGTERM)
   659	            Q->>W: 终止进程
   660	            API->>DB: UPDATE task SET status=CANCELLED, error="强制终止"
   661	        end
   662	    else 已完成/已取消
   663	        API-->>U: 409 {code:20003, message:"任务状态不允许取消"}
   664	    end
   665	```
   666	
   667	**取消后的中间数据清理策略**：
   668	- `agent_messages`、`tool_calls`、`task_executions` 记录**保留**，用于调试和回放
   669	- LangGraph 检查点保留，可通过 trace 接口查看取消前的执行路径
   670	- 不自动删除任务记录，由用户手动清理或 CLI 批量清理
   671	
   672	### 3.5 任务结果回调链路（P1-5 修正）
   673	
   674	#### 3.5.1 回调注册
   675	
   676	任务提交时通过 `callback_url` 可选字段注册回调：
   677	
   678	```json
   679	POST /api/v1/tasks
   680	{
   681	  "input": "调研 LangGraph 最新特性",
   682	  "scenario": "research",
   683	  "callback_url": "https://example.com/webhook/task-complete"
   684	}
   685	```
   686	
   687	回调 URL 存储在 `tasks.callback_url` 字段。
   688	
   689	#### 3.5.2 回调触发与重试
   690	
   691	| 触发时机 | 回调载荷 | 重试策略 |
   692	|---|---|---|
   693	| 任务完成（COMPLETED） | `{task_id, status:"COMPLETED", result, completed_at, duration_seconds}` | 失败后指数退避：1s → 3s → 9s，最多 3 次 |
   694	| 任务失败（FAILED） | `{task_id, status:"FAILED", error_message, completed_at}` | 同上 |
   695	| 任务取消（CANCELLED） | `{task_id, status:"CANCELLED", completed_at}` | 同上 |
   696	
   697	**回调实现**：
   698	- `CallbackService` 使用 `httpx.AsyncClient` 发送 POST
   699	- 超时 10s，非 2xx 响应视为失败
   700	- 重试在 Celery 任务内同步执行（不另开任务，避免复杂度）
   701	- 回调失败仅记录日志，不影响任务本身状态
   702	- 回调请求头包含 `X-Task-Id` 和 `X-Signature`（可选 HMAC 签名，预留扩展）

   705	
   706	```mermaid
   707	graph LR
   708	    subgraph "Celery Worker 池 (concurrency=4)"
   709	        W1[Worker 进程 1]
   710	        W2[Worker 进程 2]

   734	### 3.7 任务状态查询与缓存链路（P1-6 修正）
   735	
   736	```mermaid
   737	sequenceDiagram
   738	    participant U as 前端
   739	    participant API as FastAPI
   740	    participant REDIS as Redis
   741	    participant DB as SQLite
   742	
   743	    U->>API: GET /api/v1/tasks/{task_id}
   744	    API->>REDIS: GET task:{task_id}
   745	    alt 缓存命中且状态为稳定状态(COMPLETED/FAILED/CANCELLED)
   746	        REDIS-->>API: 缓存数据 (TTL=30s)
   747	    else 缓存未命中或 RUNNING 状态
   748	        API->>DB: SELECT * FROM tasks WHERE id = ?
   749	        DB-->>API: 任务记录
   750	        alt 状态为稳定状态(COMPLETED/FAILED/CANCELLED)
   751	            API->>REDIS: SETEX task:{task_id} 30s (仅缓存稳定状态)
   752	        else 状态为 PENDING/RUNNING
   753	            Note over API: 不缓存, 避免返回过时状态
   754	        end
   755	    end
   756	    API-->>U: {task_id, status, result, ...}
   757	```
   758	
   759	**缓存主动失效机制**（P1-6）：
   760	- Worker 每次更新 tasks 表状态后（PENDING→RUNNING、RUNNING→COMPLETED/FAILED），立即执行 `DEL task:{task_id}`
   761	- RUNNING/PENDING 状态**不写入缓存**，仅缓存终态（COMPLETED/FAILED/CANCELLED）
   762	- 终态缓存 TTL=30s，失效后回源 DB
   763	- 取消操作（cancellation_requested）后也执行 DEL

   800	### 3.9 检查点回放与恢复链路（P1-10 修正）
   801	
   802	**区分两个概念**：
   803	
   804	| 能力 | 说明 | 接口 | 语义 |
   805	|---|---|---|---|
   806	| **回放（Replay）** | 只读查看历史执行状态 | `GET /api/v1/tasks/{task_id}/trace` | 返回 agent_messages + tool_calls + 检查点快照列表，不重新执行 |
   807	| **恢复（Resume）** | 从检查点重新执行 | `POST /api/v1/tasks/{task_id}/resume` | 从指定 checkpoint 重新 `StateGraph.invoke()`，任务状态置 RUNNING 继续 |
   808	
   809	#### 3.9.1 回放链路
   810	
   811	```mermaid
   812	sequenceDiagram
   813	    participant U as 用户
   814	    participant API as FastAPI
   815	    participant DB as SQLite
   816	    participant CKPT as Checkpointer DB
   817	
   818	    U->>API: GET /api/v1/tasks/{task_id}/trace?page=1&page_size=20
   819	    API->>DB: SELECT agent_messages, tool_calls WHERE task_id=? (分页)
   820	    DB-->>API: 消息与调用记录
   821	    API->>CKPT: SqliteSaver.list(thread_id=task_id)
   822	    CKPT-->>API: 检查点快照列表（checkpoint_id, 节点名, 状态）
   823	    API-->>U: {messages, tool_calls, checkpoints, pagination}
   824	```
   825	
   826	#### 3.9.2 恢复链路
   827	
   828	```mermaid
   829	sequenceDiagram
   830	    participant U as 用户
   831	    participant API as FastAPI
   832	    participant DB as SQLite
   833	    participant Q as Celery+Redis
   834	    participant W as Celery Worker
   835	    participant LG as LangGraph
   836	    participant CKPT as Checkpointer DB
   837	
   838	    U->>API: POST /api/v1/tasks/{task_id}/resume {checkpoint_id?}
   839	    API->>DB: 验证任务状态为 FAILED/CANCELLED
   840	    API->>DB: UPDATE task SET status=PENDING, error_message=NULL
   841	    API->>Q: delay resume_task(task_id, checkpoint_id)
   842	    API-->>U: 202 {task_id, status:PENDING}
   843	
   844	    Q->>W: 分发恢复任务
   845	    W->>CKPT: SqliteSaver.get(thread_id=task_id, checkpoint_id)
   846	    CKPT-->>W: 历史状态快照
   847	    W->>LG: StateGraph.invoke(None, config={thread_id, checkpoint_id})
   848	    Note over LG: 从检查点节点继续执行<br/>(跳过已完成的子任务)
   849	    LG-->>W: 最终状态
   850	    W->>DB: UPDATE task SET status=COMPLETED
   851	```
   852	
   853	**恢复限制**：
   854	- 仅允许 FAILED / CANCELLED 状态的任务恢复，COMPLETED 任务返回 409
   855	- `checkpoint_id` 可选，不传则从最新检查点恢复
   856	- 恢复后任务重新进入正常执行流程（含回调通知）
   857	- 恢复功能为 **P1 优先级**，本期实现基础版本；若时间紧张可降级为仅支持回放，恢复标记为后续优化

  1169	### 4.5 LangGraph 检查点存储
  1170	
  1171	LangGraph 的 `SqliteSaver` 使用独立的 SQLite 文件（`data/checkpoints/checkpoints.db`），内部表结构由 LangGraph 管理（`checkpoints`、`checkpoint_writes`、`checkpoint_blobs`），不与业务库混用。通过 `thread_id = task_id` 关联业务任务。
  1172	
  1173	- **回放**：`SqliteSaver.list(thread_id=task_id)` 获取所有检查点（P1-10）
  1174	- **恢复**：`StateGraph.invoke(None, config={"configurable": {"thread_id": task_id}, "checkpoint_id": ...})`（P1-10）

  1176	### 4.6 数据库迁移策略（P2-6 修正）
  1177	
  1178	| 阶段 | 时间 | 策略 |
  1179	|---|---|---|
  1180	| 开发初期 | 第 1-3 周 | `SQLAlchemy create_all()` 自动建表，表结构频繁变动时直接删库重建 |
  1181	| 表结构稳定后 | 第 4 周起 | 引入 Alembic，生成初始 migration 脚本，后续变更通过 `alembic revision --autogenerate` 管理 |
  1182	| 交付时 | 第 6 周 | 提供初始 migration + 完整 schema，确保干净环境可复现 |
  1183	
  1184	**理由**：项目初期表结构频繁变动，Alembic 迁移脚本维护成本高（尤其 SQLite 的 DDL 限制）；第 4 周核心模块完成后表结构基本稳定，此时引入 Alembic 性价比最高。

  1289	
  1290	鉴于基线明确排除多租户/用户权限体系（X-02），采用**轻量级 API Key 机制**：

  1613	## 8. 技术风险与应对方案
  1614	
  1615	### 8.1 核心风险
  1616	
  1617	#### 风险 R-01：LangGraph 状态管理复杂度
  1618	
  1619	| 项 | 内容 |
  1620	|---|---|
  1621	| **风险描述** | 多 Agent 协作涉及 Planner→Executor→Reviewer 循环 + 子任务遍历条件路由，StateGraph 状态字段多、流转复杂，易出现状态不一致或死循环 |
  1622	| **影响范围** | C-01 编排引擎，M-03 完成率、M-04 可追溯率 |
  1623	| **概率** | 高 |
  1624	| **严重度** | 高 |
  1625	| **应对方案** | ① 状态字段用 TypedDict 严格定义，每个节点只写入自己负责的字段；② `current_subtask_idx` 显式控制子任务遍历（P1-1 修正）；③ 设置 `max_rounds=5` 硬上限防止死循环（M-02）；④ Reviewer 不通过最多重试 2 次后强制通过并记录 warning；⑤ Executor 节点内工具调用循环 `max_tool_calls=5`；⑥ 单元测试覆盖每条状态转移路径 |
  1626	
  1627	#### 风险 R-02：MCP 协议稳定性与工具调用可靠性
  1628	
  1629	| 项 | 内容 |
  1630	|---|---|
  1631	| **风险描述** | MCP 协议尚在快速演进，Python SDK API 可能变更；stdio 传输在子进程管理上易泄漏；工具执行异常可能导致 Agent 卡死 |
  1632	| **影响范围** | C-02 MCP 工具层，T-02 调用成功率 |
  1633	| **概率** | 中 |
  1634	| **严重度** | 高 |
  1635	| **应对方案** | ① 锁定 MCP SDK 版本（`mcp==0.1.x`），不随意升级；② **任务级 Session + try/finally + 子进程 terminate/kill**（P1-2 修正）；③ 工具调用设置 30s 超时，超时返回结构化错误；④ 工具适配器统一 try/except，异常转为 ToolMessage error 格式；⑤ JSON Schema 参数校验前置（T-04）；⑥ 禁止 print 到 stdout，统一 logging（P1-2）；⑦ 孤儿进程监控与清理 |
  1636	
  1637	#### 风险 R-03：LLM API 不稳定与预算超限
  1638	
  1639	| 项 | 内容 |
  1640	|---|---|
  1641	| **风险描述** | 外部 LLM API 可能限流、超时、返回格式异常；API 预算 ≤¥200，评测 30 用例 × 多轮调用可能超支 |
  1642	| **影响范围** | 全链路，E-04 评测时间、Q-02 性能 |
  1643	| **概率** | 中 |

  1645	| **应对方案** | ① LLM Gateway 指数退避重试（最多 3 次，初始 1s）；② 响应格式校验，非预期 JSON 时自动重试；③ **Mock 模式**：`--mock` 参数零成本调试；④ **llm_usage 表持久化计费 + ¥180 阈值强制 Mock**（P1-9 修正）；⑤ 评测用例支持分批执行（`--category` 筛选）；⑥ 温度设为 0 降低输出随机性 |

  1647	#### 风险 R-04：LLM-as-Judge 评分一致性不足
  1648	
  1649	| 项 | 内容 |
