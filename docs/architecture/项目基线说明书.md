# 《项目基线说明书》

**项目名称**：多智能体编排与模型评测一体化平台
**文档版本**：v1.0
**基线日期**：2026-10-05
**优先级**：P1（★★★★☆）

---

## 一、项目核心目标

### 1.1 核心问题
当前 AI Agent 开发与评估存在三大断层：
- **编排断层**：单 Agent 无法处理复杂多步任务，缺乏可观测、可回滚的多 Agent 协作机制
- **工具断层**：Agent 调用外部工具依赖硬编码集成，缺少标准化协议（MCP）实现工具即插即用
- **评测断层**：模型/Agent 输出质量依赖人工主观判断，缺乏可复现、可对比的量化评测体系

### 1.2 业务价值
| 维度 | 价值描述 |
|---|---|
| 工程能力 | 构建可复用的多 Agent 编排框架，支持任务拆解、角色分工、结果汇总的完整闭环 |
| 标准化 | 基于 MCP 协议实现工具层解耦，新增工具无需修改 Agent 核心代码 |
| 可评估 | 建立自动化评测流水线，对 Agent 输出进行多维度打分与回归对比 |
| 求职竞争力 | 覆盖 LangGraph、MCP、模型评测三大 Agent 岗位高频考点，技术深度高于普通 RAG/单 Agent 项目 |

## 二、核心指标量化

### 2.1 多 Agent 编排指标

| 指标编号 | 指标名称 | 量化目标 | 验证方式 |
|---|---|---|---|
| M-01 | 支持的 Agent 角色数 | ≥ 3 个独立角色（如 Planner / Executor / Reviewer） | 代码中可枚举的 Agent 类数量 |
| M-02 | 单任务最大协作轮次 | ≥ 5 轮 Agent 间消息传递 | 运行日志中 inter-agent message 计数 |
| M-03 | 复杂任务完成率 | 在 10 个标准测试用例上，端到端完成率 ≥ 80% | 评测脚本自动统计 pass/total |
| M-04 | 编排状态可追溯率 | 100% 的执行步骤可通过 LangGraph state 回放 | 检查点恢复测试，任意节点可重入 |
| M-05 | 单任务平均响应延迟 | P50 ≤ 30s，P95 ≤ 90s（本地部署条件下） | 10 次运行取百分位 |

### 2.2 MCP 工具调用指标

| 指标编号 | 指标名称 | 量化目标 | 验证方式 |
|---|---|---|---|
| T-01 | 接入的 MCP 工具数 | ≥ 4 个（如 网页搜索 / 代码执行 / 文件读写 / 数据库查询） | MCP server 注册的 tool 清单 |
| T-02 | 工具调用成功率 | 在 20 次工具调用测试中成功率 ≥ 90% | 调用日志中 success/total |
| T-03 | 新增工具接入成本 | 新增 1 个工具的代码改动量 ≤ 50 行，且不修改 Agent 核心逻辑 | 代码 diff 行数统计 |
| T-04 | 工具参数校验覆盖率 | 100% 工具调用前执行 JSON Schema 参数校验 | 单元测试覆盖 |

### 2.3 模型评测指标

| 指标编号 | 指标名称 | 量化目标 | 验证方式 |
|---|---|---|---|
| E-01 | 评测维度数 | ≥ 4 个维度（准确性 / 相关性 / 完整性 / 格式合规性） | 评测配置文件中维度定义数 |
| E-02 | 评测用例库规模 | ≥ 30 条标注用例，每条含输入、期望输出、评分标准 | 用例文件行数/条数 |
| E-03 | 评测自动化率 | 100% 用例可通过单条命令批量执行并输出报告 | CLI 一键运行验证 |
| E-04 | 评测报告生成时间 | 30 条用例全量评测 ≤ 5 分钟 | 计时运行 |
| E-05 | 评分一致性 | LLM-as-Judge 与人工评分的 Spearman 相关系数 ≥ 0.7 | 10 条用例双盲对比 |

### 2.4 系统工程指标

| 指标编号 | 指标名称 | 量化目标 | 验证方式 |
|---|---|---|---|
| S-01 | 核心代码单元测试覆盖率 | ≥ 60%（行覆盖率） | pytest-cov 报告 |
| S-02 | API 接口数 | ≥ 5 个 RESTful 端点（任务提交 / 状态查询 / 结果获取 / 评测触发 / 报告下载） | OpenAPI 文档枚举 |
| S-03 | 文档完整度 | README + 架构图 + API 文档 + 部署指南，合计 ≥ 2000 字 | 文档字数统计 |
| S-04 | 一键启动能力 | 单条命令（docker-compose up 或 make run）可启动完整系统 | 干净环境下验证 |

## 三、项目范围界定

### 3.1 核心范围（必须做，MoSCoW = Must）

| 编号 | 模块 | 交付物 | 完成定义 |
|---|---|---|---|
| C-01 | LangGraph 多 Agent 编排引擎 | 可运行的状态图定义 + 3 个 Agent 角色 | 能跑完 10 个标准用例，完成率 ≥ 80% |
| C-02 | MCP 协议工具服务层 | MCP Server + ≥ 4 个工具适配器 | Agent 可通过 MCP 动态发现并调用工具 |
| C-03 | 基础评测框架 | 评测引擎 + 用例库 + 评分模块 + 报告生成器 | 30 条用例一键评测并输出结构化报告 |
| C-04 | 任务编排 API 层 | RESTful API + 任务队列 | 支持异步提交、状态轮询、结果回调 |
| C-05 | 执行可观测性 | 运行日志 + LangGraph 检查点 + 调用链路追踪 | 任意已完成任务可回放完整执行路径 |

### 3.2 配套范围（辅助做，MoSCoW = Should）

| 编号 | 模块 | 交付物 | 完成定义 |
|---|---|---|---|
| P-01 | Web 操作界面 | 简易前端页面（任务提交 + 结果展示 + 评测报告查看） | 可通过浏览器完成核心操作，不追求 UI 精美 |
| P-02 | 本地模型接入 | 支持 1 个本地模型（如 Ollama 部署的 Qwen2.5-7B）作为可选推理后端 | 可切换 API 模型 / 本地模型，功能等价 |
| P-03 | 示例场景 Demo | ≥ 2 个端到端 Demo（如 调研报告生成 / 代码审查助手） | Demo 可复现，含输入输出样例 |
| P-04 | 配置管理 | 统一配置文件（模型参数、Agent 角色、工具开关） | 修改配置无需改代码 |

### 3.3 排除范围（明确不做，MoSCoW = Won't）

| 编号 | 排除项 | 排除理由 |
|---|---|---|
| X-01 | 分布式多节点部署 / K8s 编排 | 超出项目定位，本地单机即可验证核心价值 |
| X-02 | 多租户体系 / 用户权限管理 | 求职项目无需企业级多租户，增加复杂度无收益 |
| X-03 | 模型微调 / 训练流水线 | 项目聚焦编排与评测，不涉及模型训练 |
| X-04 | 商业化支付 / 计费系统 | 无实际付费场景，属于过度设计 |
| X-05 | 移动端适配 | 仅需桌面端 Web 可用 |
| X-06 | 生产级高可用 / 灾备 | 单机部署，不承诺 SLA |
| X-07 | 自研大模型推理引擎 | 直接调用现有 API 或 Ollama，不重复造轮子 |

## 四、约束条件

### 4.1 技术栈约束

| 类别 | 约束 | 说明 |
|---|---|---|
| 编排框架 | **必须**使用 LangGraph | 项目核心卖点，不可替换为 AutoGen / CrewAI |
| 工具协议 | **必须**实现 MCP（Model Context Protocol） | 标准化工具调用，不可用自定义 RPC 替代 |
| 主语言 | Python ≥ 3.10 | 与 LangGraph / LangChain 生态兼容 |
| LLM 接入 | 优先使用 OpenAI 兼容 API（如 DeepSeek / 通义千问） | 本地模型为可选，不作为默认 |
| 存储 | SQLite（任务记录 + 评测结果） | 不引入 MySQL/PostgreSQL，降低部署复杂度 |
| 前端（如做） | 纯 HTML + 原生 JS 或 Gradio | 不引入 React/Vue 重型框架 |
| 版本管理 | Git，提交信息使用 Conventional Commits | 仓库需有完整提交历史 |

### 4.2 部署环境约束

| 约束项 | 规格 |
|---|---|
| 操作系统 | Windows 10/11 或 Ubuntu 22.04+（开发机） |
| 内存 | ≥ 16GB（使用 API 模型时）；≥ 32GB（启用本地 7B 模型时） |
| GPU | 非必需；启用本地模型时建议 ≥ 8GB 显存 |
| 网络 | 需可访问 LLM API 端点（开发阶段） |
| 容器化 | 提供 Dockerfile + docker-compose.yml，确保干净环境可复现 |

### 4.3 资源约束

| 约束项 | 限制 |
|---|---|
| 开发人力 | 1 人（独立开发） |
| API 调用预算 | 累计 ≤ ¥200（评测 + 开发调试），需在评测框架中支持 mock 模式降低消耗 |
| 本地存储 | 项目代码 + 数据 ≤ 2GB |
| 第三方服务 | 不依赖付费 SaaS（除 LLM API 外） |

### 4.4 时间约束

| 阶段 | 周期 | 里程碑 |
|---|---|---|
| 总体开发周期 | ≤ 6 周（从基线确认日起算） | 2026-11-16 前完成全部核心范围 |
| 第 1-2 周 | LangGraph 编排 + MCP 工具层 | C-01、C-02 可运行 |
| 第 3-4 周 | 评测框架 + API 层 | C-03、C-04 可运行 |
| 第 5 周 | 可观测性 + 集成联调 | C-05 完成，全链路打通 |
| 第 6 周 | 配套范围 + 文档 + Demo + 验证 | 全部交付物就绪 |

### 4.5 合规约束

| 约束项 | 要求 |
|---|---|
| 数据隐私 | 评测用例不得包含真实个人隐私数据，使用合成或公开数据 |
| API 密钥管理 | 密钥通过环境变量注入，不得硬编码提交至 Git 仓库 |
| 开源许可 | 引入的第三方库许可证需兼容（MIT / Apache 2.0 / BSD），禁止引入 GPL 传染性协议库 |
| 模型使用 | 遵守所调用 LLM API 的使用条款，评测数据不得用于违反条款的场景 |
